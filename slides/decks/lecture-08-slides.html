Lecture 08 — Testing Before Trusting

Learning objectives

  • Design test cases from requirements, not from the code
  • Choose boundary and edge cases deliberately
  • Write simple assert-based checks

Case-based lecture: you attempt, we discuss, then we reveal.

Key definitions

Key definitions

  • Test case — one input plus the output the specification demands.
  • Test table — a systematic list of cases grouped by purpose: normal, boundary, adversarial.
  • Normal case — typical use the code was written for.
  • Boundary case — an input exactly at a rule's edge (0, empty, the allowed maximum).
  • Adversarial case — an input designed to break careless code (negatives, junk text, huge values).
  • Black-box testing — designing cases from the specification alone.
Explain each in one breath; the cases will do the heavy lifting.
Worked example

The triangle classifier: building the test table

cs-029

Classify triangles: scalene, isosceles, equilateral, impossible (degenerate), invalid. Design the test table before the classifier.

Expected: six verdict lines matching the reference

Cost: O(1) per input; the intellectual work is the table, not the branches.

Worked example

Black box vs white box on the fee function

cs-031

fee(x): 0 below 3, 2 up to 5, 5 above. A buggy version charges 0 at exactly x = 3. Which suite finds it - black box or white box?

def classify(a, b, c):
    sides = sorted([a, b, c])
    if sides[0] + sides[1] <= sides[2]:
        return "invalid"
    if a == b == c:
        return "equilateral"
    if a == b or b == c or a == c:
        return "isosceles"
    return "scalene"

print(classify(3, 4, 5), classify(5, 5, 5), classify(4, 4, 7), classify(1, 2, 8))

Expected: rows ending with a disagreement exactly at x = 3

Cost: Suite size stays small (4-8 rows) because white-box targeting hits the seams instead of sampling blindly.

Case cs-031 · Intermediate

Black Box vs White Box

Given a small function with tricky internal branches, compare the tests a black-box tester writes with the tests the code's structure demands. Which defect escapes which suite?

  • **Input:** def fee(x): if x < 3: return 0; elif x <= 5: return 2; else: return 5
  • **Output:** black-box misses x=3 exactly (0 vs 2 boundary) and negative x; white-box adds both; the escaped defect is 'x < 3' vs 'x <= 3'

Check yourself

Common misconceptions

  • Testing only the happy path - boundaries are where defects live.
  • One random outcome deciding a random function's fate.
  • Full line coverage mistaken for correctness.
  • Adversarial cases dismissed as 'unrealistic' - users are adversarial by nature.
