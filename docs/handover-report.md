## 2 · Technology stack

- **Content:** plain Markdown; cases and lectures follow a fixed section
  contract enforced by `scripts/validate.py`.
- **Tooling:** Python 3 (developed and tested on 3.12), **standard library
  only** — no runtime dependencies. `pytest==8.3.4` is the single dev
  dependency (`requirements-dev.txt`).
- **Website:** dependency-free static HTML + one stylesheet generated by
  `scripts/build_site.py`; browser-side search over `pages.json`.
- **Slides:** generated HTML decks from lecture sources via
  `scripts/gen_slides.py` (no proprietary application needed).
- **CI/CD:** GitHub Actions; one validation workflow, one deployment
  workflow (`upload-pages-artifact` + `deploy-pages`).

## 3 · Commands

```bash
# --- validation (run after any content change) ---
python scripts/validate.py         # structure, links, case pairing, metadata
python -m pytest tests/ -q         # tooling tests
python scripts/qa_report.py        # full suite + qa-report.md

# --- regeneration (only when content changed) ---
python scripts/generate_catalog.py # case catalog from metadata
python scripts/gen_slides.py       # slide decks from lecture sources

# --- builds ---
python scripts/build_site.py       # public student site → site/
python scripts/build_instructor.py # everything → public_instructor/ (local)

# --- preview ---
python -m http.server 8000 --directory site
# open http://localhost:8000/   (Ctrl+C to stop)

# --- audit of the built site (optional) ---
python scripts/audit_site.py       # pages, references, broken links
```

Regenerating overwrites generated files; hand-edit sources, not output.

## 4 · GitHub Pages setup requirements

One manual setting, then everything is automatic:

1. Repository **Settings → Pages → Build and deployment → Source:
   `GitHub Actions`**. The deployment workflow does not run correctly until
   this is chosen.
2. Push to `main` (or use **Run workflow** in the Actions tab). The workflow
   validates → regenerates → builds → leak-checks → uploads → deploys; every
   stage gates the next, so a failing validation blocks publication.
3. First deployment creates the `github-pages` environment automatically.
   No secrets, no branch selection, no other settings.

See [Deployment](deployment.md) for the gate table and local reproduction of
the full pipeline.

## 5 · Instructor-only content handling

**What is instructor-only:** `case-studies/instructor/`, every `keys/`
directory (quizzes, labs), assignment marking keys, lecture
`teaching-notes.md`, the activities facilitation map, and
`docs/instructor-reports/` (they quote reference output — answers in
disguise).

**How separation is enforced:**

- `scripts/build_site.py` excludes all of these by path and runs a leak scan
  over its own output; any hit fails the build, and the deployment workflow
  re-verifies the artifact before upload.
- `scripts/build_instructor.py` produces the complete `public_instructor/`
  build for your own devices; that directory is gitignored and is **never**
  run or uploaded by the deployment workflow.
- `scripts/validate.py` verifies the 144 student/instructor pairs and the
  lecture↔case mappings on every run.

**Your responsibility:** never deploy `public_instructor/` anywhere public,
and distribute solutions through your institution's access-controlled system
(LMS, shared drive). A private-looking folder on a public host is not
protection — build-time exclusion is the control that matters. Full policy:
[Instructor Guide → Instructor-only materials](instructor-guide.md#instructor-only-materials-and-distribution).

## 6 · Known limitations

1. **Line endings:** repository files use CRLF; Python reads them
   transparently, but `git diff` output may look noisy across platforms
   unless you set a `.gitattributes` policy (see remaining tasks).
2. **Case-count notes, not warnings:** fourteen lectures carry more than the
   base four cases (the applied additions cs-129–cs-144). The validator
   reports this as informational by design — not a defect.
3. **Slides are generated:** hand-editing `slides/decks/*.html` is lost on
   regeneration; edit lecture sources and re-run `gen_slides.py`.
4. **Search is client-side:** `search.html` is excellent for a course corpus
   but is not a server-side engine; fine at this scale.
5. **No gradebook:** the assessment plan defines weights and rubrics; marks
   live in your institution's system, not here.
6. **Determinism of randomness:** the two simulation cases use fixed seeds;
   if you replace data, keep the seeds so expected outputs stay true.
7. **Python version:** tooling targets 3.10+ (validated on 3.12); lecture
   Python is deliberately conservative (no 3.11+-only syntax).
