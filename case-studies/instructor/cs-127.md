## Reference solution (pseudocode)

FUNCTION profile(rows)
    stats <- map{'rows': LENGTH(rows), 'missing_hours': 0, 'dup_ids': 0, 'over_24': 0}
    seen <- SET()
    FOR EACH r IN rows DO
        h <- r.get('hours')
        IF h is null THEN
            stats['missing_hours'] <- stats['missing_hours'] + 1
        ELSE IF h > 24 THEN
            stats['over_24'] <- stats['over_24'] + 1
        IF r['id'] in seen THEN
            stats['dup_ids'] <- stats['dup_ids'] + 1
        add r['id'] to seen
    RETURN stats
FUNCTION clean_and_summarise(rows)
    st <- profile(rows)
    hours <- {r['hours'] for each r in rows AND (r.get('hours') is not null) AND (r['hours'] <= 24)}
    hours.sort()
    n <- LENGTH(hours)
    med <- (hours[n div 2] if n mod 2 else (hours[n div 2 - 1] + hours[n div 2]) / 2)

## Reference solution (Python)

```python
def profile(rows):
    # rows: list of dicts with keys id, hours
    stats = {"rows": len(rows), "missing_hours": 0, "dup_ids": 0, "over_24": 0}
    seen = set()
    for r in rows:
        h = r.get("hours")
        if h is None:
            stats["missing_hours"] += 1
        elif h > 24:
            stats["over_24"] += 1
        if r["id"] in seen:
            stats["dup_ids"] += 1
        seen.add(r["id"])
    return stats

def clean_and_summarise(rows):
    st = profile(rows)
    hours = [r["hours"] for r in rows
             if r.get("hours") is not None and r["hours"] <= 24]
    hours.sort()
    n = len(hours)
    med = hours[n // 2] if n % 2 else (hours[n // 2 - 1] + hours[n // 2]) / 2
    return st, med, f"N={n} after cleaning"

if __name__ == "__main__":
    data = [{"id": 1, "hours": 7}, {"id": 1, "hours": 7}, {"id": 2, "hours": None},
            {"id": 3, "hours": 25}, {"id": 4, "hours": 6.5}]
    print(clean_and_summarise(data))
```

## Edge cases

- Base case: what is the smallest input, and does every path reach it?
- First occurrence of a key not yet in the map — the default path must produce a defined answer.
- Ties: two equal values may swap order in the input; the stated rule must pin the output.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Boundary positions: the first item, the last item, and the position one past each end (the i-1 / i+1 arithmetic).


## Alternative approaches

- Full pipeline, small data: profile first (counts per defect), THEN policies, then the summary states its N.
- Loop-first formulation versus a comprehension/direct-expression formulation — same result, different emphasis on state versus intent.
- Sort first, then scan once, versus scanning with extra bookkeeping and no sort: the sort pays for itself only when later steps reuse the order.
- **Cost.** The sort dominates the cost: n log n in the input size, everything after it is one cheap pass; the alternatives shift exactly this cost.


## Common pitfalls

- Hiding a value judgement inside 'obvious' arithmetic.
- Reading a key before it exists (the first occurrence) instead of using the default path.
- Mutating the caller's list when the result was meant to be a fresh one — the demo where the input 'changes by itself'.
- Comparing floating-point values for exact equality instead of a tolerance (or rounding at the very end, not mid-computation).
- Off-by-one at the boundary: the update that is correct for the middle of the data and wrong at the two ends.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'Which quantity does the rule attach to, and what exactly does one application of the rule change?'
3. Walk the worked instance (rows with missing hours, duplicate ids, one 25-hour day, mixed am/pm) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'hiding a value judgement inside 'obvious' arithmetic' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "modelling, rules, and decisions" — and hand over the
   discussion prompt: **"Propose one extra rule that would change the verdict — is it an improvement?"**


## Assessment use

- **Formative use.** discussion-grade: mark assumption quality and rule precision rather than the final number, and expect the full cycle to run long.
- **Mini-rubric (10 points).**
  - *Structure (2):* inputs, outputs, and the binding constraint named before any computation.
  - *Method (3):* the stated moves executed — especially "State assumptions explicitly (what is fixed, what varies)"
    and "Write the decision procedure as precise rules".
  - *Result (3):* the worked instance computed correctly (profile -> clean (typed policies per defect) -> honest summary…),
    and the answer survives the smallest and the boundary input.
  - *Communication (2):* assumptions stated; the answer reports which rule produced it.
- **Follow-up check.** A key appears that was never seen before: which line of your rule handles it, and what does it output?
