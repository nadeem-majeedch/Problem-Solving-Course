## Reasoning walkthrough

**Worked instance.** secret in 1..100; each guess answered 'high/low/correct'

**Expected result.** 7 guesses always suffice: ceil(log2 101); 6 for most, 7 worst case

**Method — binary search on data or answers.** Walk the class through these moves:

1. Identify the monotone structure: what switches exactly once (or sorts the world)?
2. Maintain the half-open interval that must contain the answer.
3. Update bounds so the interval strictly shrinks every step.
4. Argue termination and the meaning of the final interval.

**Where this class gets stuck.** Halving argument with a drawing: after k questions, remaining <= 100 / 2^k; force it below 1. Expect the first
five minutes to produce hi = mid - 1 with a 'first true' question skips the answer as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step
computation on the instance; a correct rule with an arithmetic slip is
partial credit. Watch for: the input update that looks right but stalls on the smallest instance — have them test an interval of size two.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder
(below) whole-class rather than pair by pair.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (Python)

```python
def worst_guesses(lo=1, hi=100):
    count = 0
    while lo < hi:
        mid = (lo + hi) // 2
        lo = mid + 1   # worst case: always 'higher'
        count += 1
    return count + 1   # the final guess that lands

if __name__ == "__main__":
    print(worst_guesses())   # 7
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.


## Edge cases

- Termination: name the update that guarantees the loop ends, and check it on the smallest input.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Boundary positions: the first item, the last item, and the position one past each end (the i-1 / i+1 arithmetic).


## Alternative approaches

- Halving argument with a drawing: after k questions, remaining <= 100 / 2^k; force it below 1.
- Rewrite the while-loop as a bounded for-loop over the data (or vice versa) and compare which version makes termination obvious.
- A table filled by hand before any code: for the size of instance here it is both a solution and the test oracle.
- **Cost.** Logarithmic: the interval (or exponent) halves every step, so doubling the input adds one step; the alternatives shift exactly this cost.


## Common pitfalls

- Hi = mid - 1 with a 'first true' question skips the answer.
- An update path that never moves the state — the loop that never ends; test on an interval of size two.
- Off-by-one at the boundary: the update that is correct for the middle of the data and wrong at the two ends.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'What switches exactly once — and can your test actually see it?'
3. Walk the worked instance (secret in 1..100; each guess answered 'high/low/correct') on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'hi = mid - 1 with a 'first true' question skips the answer' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "binary search on data or answers" — and hand over the
   discussion prompt: **"What would you do if the predicate were monotone 'almost everywhere' with one glitch?"**


## Assessment use

- **Formative use.** discussion-grade: mark assumption quality and rule precision rather than the final number, and expect the full cycle to run long.
- **Mini-rubric (10 points).**
  - *Structure (2):* inputs, outputs, and the binding constraint named before any computation.
  - *Method (3):* the stated moves executed — especially "Maintain the half-open interval that must contain the answer"
    and "Update bounds so the interval strictly shrinks every step".
  - *Result (3):* the worked instance computed correctly (7 guesses always suffice: ceil(log2 101); 6 for most, 7 worst…),
    and the answer survives the smallest and the boundary input.
  - *Communication (2):* assumptions stated; the answer reports which rule produced it.
- **Follow-up check.** Which update line guarantees termination? Delete it mentally: what goes wrong first?
