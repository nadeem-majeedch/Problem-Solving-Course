## Reasoning walkthrough

**Worked instance.** cohort A app minutes [120, 90, 150]; cohort B [60, 45, 75]; cohort C [200, 180, 210, 190]

**Expected result.** A mean 120, B mean 60, C mean 195; shares of total usage differ from headcount shares

**Method — modelling, rules, and decisions.** Walk the class through these moves:

1. Extract the entities, quantities, and rules from the story.
2. State assumptions explicitly (what is fixed, what varies).
3. Write the decision procedure as precise rules.
4. Run the rules on the worked instance; sanity-check the output.

**Where this class gets stuck.** Compute mean AND share of total; the two rankings can disagree - that disagreement is the finding. Expect the first
five minutes to produce hiding a value judgement inside 'obvious' arithmetic as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step
computation on the instance; a correct rule with an arithmetic slip is
partial credit. Watch for: reading an input key before it exists — the first occurrence needs the default path.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder
(below) whole-class rather than pair by pair.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (pseudocode)

FUNCTION cohort_report(groups)
    means <- map{g: SUM(v) / LENGTH(v) for (g, v) in (groups items)}
    totals <- map{g: SUM(v) for (g, v) in (groups items)}
    grand <- SUM((totals values))
    shares <- map{g: t / grand for (g, t) in (totals items)}
    RETURN (means, shares)
// demo run: OUTPUT cohort_report(map{'A': [120, 90, 150], 'B': [60, 45, 75], 'C': [200, 180, 210, 190]})


## Reference solution (Python)

```python
def cohort_report(groups):
    means = {g: sum(v) / len(v) for g, v in groups.items()}
    totals = {g: sum(v) for g, v in groups.items()}
    grand = sum(totals.values())
    shares = {g: t / grand for g, t in totals.items()}
    return means, shares

if __name__ == "__main__":
    print(cohort_report({"A": [120, 90, 150], "B": [60, 45, 75], "C": [200, 180, 210, 190]}))
```

## Edge cases

- First occurrence of a key not yet in the map — the default path must produce a defined answer.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.


## Alternative approaches

- Compute mean AND share of total; the two rankings can disagree - that disagreement is the finding.
- Loop-first formulation versus a comprehension/direct-expression formulation — same result, different emphasis on state versus intent.
- A plain list of (key, value) pairs instead of a map: fine at this size, but every lookup becomes a scan.


## Common pitfalls

- Hiding a value judgement inside 'obvious' arithmetic.
- Reading a key before it exists (the first occurrence) instead of using the default path.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'Which quantity does the rule attach to, and what exactly does one application of the rule change?'
3. Walk the worked instance (cohort A app minutes [120, 90, 150]; cohort B [60, 45, 75]; cohort C [200, 180, 210,…) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'hiding a value judgement inside 'obvious' arithmetic' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "modelling, rules, and decisions" — and hand over the
   discussion prompt: **"Which assumption would you attack first if you had to argue the other side?"**


## Assessment use

- **Formative use.** discussion-grade: mark assumption quality and rule precision rather than the final number, and expect the full cycle to run long.
- **Mini-rubric (10 points).**
  - *Structure (2):* inputs, outputs, and the binding constraint named before any computation.
  - *Method (3):* the stated moves executed — especially "State assumptions explicitly (what is fixed, what varies)"
    and "Write the decision procedure as precise rules".
  - *Result (3):* the worked instance computed correctly (A mean 120, B mean 60, C mean 195; shares of total usage differ…),
    and the answer survives the smallest and the boundary input.
  - *Communication (2):* assumptions stated; the answer reports which rule produced it.
- **Follow-up check.** A key appears that was never seen before: which line of your rule handles it, and what does it output?
