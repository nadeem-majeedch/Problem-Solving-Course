## Reasoning walkthrough

**Worked instance.** [3, 1, 3, 2, 1, 3]

**Expected result.** order-keeping: [3, 1, 2]; sort-based: [1, 2, 3]; naive O(n^2): same as order-keeping

**Method — list surgery and slicing.** Walk the class through these moves:

1. Decide whether to mutate in place or build a new list.
2. Express the rearrangement with slices before writing loops.
3. Handle the wrap-around / size cases explicitly.
4. Check aliasing: who else can see this list object?

**Where this class gets stuck.** Implement all three, then time them on 10k elements - the point is the comparison, not the answer. Expect the first
five minutes to produce assigning a list to another name copies the reference, not the contents as the
most common wrong turn; plan the reveal around it.

## Reference solution (pseudocode)

FUNCTION dedup_seen(items)
    seen <- SET()
    out <- []
    FOR EACH x IN items DO
        IF x not in seen THEN
            add x to seen
            append x to out
    RETURN out
FUNCTION dedup_sorted(items)
    RETURN SORTED(SET(items))
// demo run: OUTPUT dedup_seen(data), dedup_sorted(data)


## Reference solution (Python)

```python
def dedup_seen(items):
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out

def dedup_sorted(items):
    return sorted(set(items))

if __name__ == "__main__":
    data = [3, 1, 3, 2, 1, 3]
    print(dedup_seen(data), dedup_sorted(data))
    assert dedup_seen(data) == [3, 1, 2]
```

## Edge cases

- Ties: two equal values may swap order in the input; the stated rule must pin the output.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.


## Alternative approaches

- Implement all three, then time them on 10k elements - the point is the comparison, not the answer.
- Loop-first formulation versus a comprehension/direct-expression formulation — same result, different emphasis on state versus intent.
- Sort first, then scan once, versus scanning with extra bookkeeping and no sort: the sort pays for itself only when later steps reuse the order.
- **Cost.** The sort dominates the cost: n log n in the input size, everything after it is one cheap pass; the alternatives shift exactly this cost.


## Common pitfalls

- Assigning a list to another name copies the reference, not the contents.
- Mutating the caller's list when the result was meant to be a fresh one — the demo where the input 'changes by itself'.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'Does this operation need a copy, a view, or in-place surgery — and who else can still see the list?'
3. Walk the worked instance ([3, 1, 3, 2, 1, 3]) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'assigning a list to another name copies the reference, not the contents' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "list surgery and slicing" — and hand over the
   discussion prompt: **"When is the extra memory of slicing worth it, and when would you insist on in-place?"**
