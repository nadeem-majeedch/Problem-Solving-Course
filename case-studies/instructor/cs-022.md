## Reasoning walkthrough

**Worked instance.** n = 96

**Expected result.** 96->48->24->12->6->3 (stop, odd): 5 divisions, 6 values seen

**Method — aggregation over a sequence.** Walk the class through these moves:

1. Restate what is being accumulated and over what sequence.
2. Choose the accumulator(s) and their correct starting values.
3. Decide the update rule and any filter applied before updating.
4. Decide what is reported at the end (and its type).
5. Check the accumulator initialisation against the smallest input.

**Where this class gets stuck.** Iterations = number of times 2 divides n. Write n = 2^a * b with b odd; iterations = a. Expect the first
five minutes to produce initialising best to 0 breaks when all values are negative or below target as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step
computation on the instance; a correct rule with an arithmetic slip is
partial credit. Watch for: the input update that looks right but stalls on the smallest instance — have them test an interval of size two.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder
(below) whole-class rather than pair by pair.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (pseudocode)

FUNCTION shrink_steps(n)
    steps <- 0
    WHILE n mod 2 = 0 DO
        n <- n div 2
        steps <- steps + 1
    RETURN (steps, n)
// demo run: OUTPUT shrink_steps(96)
// demo run: OUTPUT shrink_steps(1)


## Reference solution (Python)

```python
def shrink_steps(n):
    steps = 0
    while n % 2 == 0:
        n //= 2
        steps += 1
    return steps, n

if __name__ == "__main__":
    print(shrink_steps(96))    # (5, 3)
    print(shrink_steps(1))     # (0, 1) - loop may not run at all
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.


## Edge cases

- Termination: name the update that guarantees the loop ends, and check it on the smallest input.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.


## Alternative approaches

- Iterations = number of times 2 divides n. Write n = 2^a * b with b odd; iterations = a.
- Several passes with built-in helpers (a sum here, a max there) instead of one pass with several accumulators — clearer to read, more visits over the data.
- A table filled by hand before any code: for the size of instance here it is both a solution and the test oracle.


## Common pitfalls

- Initialising best to 0 breaks when all values are negative or below target.
- An update path that never moves the state — the loop that never ends; test on an interval of size two.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'What must the loop remember between two items — and what can it safely forget?'
3. Walk the worked instance (n = 96) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'initialising best to 0 breaks when all values are negative or below target' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "aggregation over a sequence" — and hand over the
   discussion prompt: **"Where exactly would this solution break first if the input grew to a million items — and would anything break at all?"**
