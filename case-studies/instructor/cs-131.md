## Reasoning walkthrough

**Worked instance.** Eight students with known arrivals and service
times; compare a one-desk and a two-desk design under FCFS rules.

**Expected result.** demo prints `one desk: waits [0, 3, 5, 6, 7, 8,
9, 10] total 48 finish 28` and `two desks: waits [0, 0, 2, 0, 1, 0, 0,
0] total 3 finish 18` — every wait is determined by the free-at trace;
with two desks only S3 (waits two minutes for the first free desk) and
S5 (one minute) wait at all.

**Method — simulation, service systems, trade-offs.** Walk the class
through these moves:

1. One desk first: the whole design is one number — `free_at`. Each
   student: `start = max(arrival, free_at)`, then `free_at = start +
   service`. Trace S1–S4 and the room will finish the pattern aloud.
2. Two desks: the state is two free-at times. Start rule: prefer desk 1
   when both are free; wait rule: take the desk that frees first.
   `start = max(arrival, min(free1, free2))` and the chosen desk's
   free-at updates.
3. Collect *both* metrics per design — total waiting and makespan —
   before comparing: a design that wins one metric can lose the other.
4. The trade-off sentence must name a condition, not a feeling: two
   desks buy 45 wait-minutes and 10 makespan-minutes here; they are
   worth it exactly when waiting cost per minute exceeds desk cost per
   minute at the traffic level observed.

**Where this class gets stuck.** The classic wrong turn is letting the
second desk "steal" a waiting student out of order or start S3 at
minute 2 on desk 2's timeline backwards (free2 starts at 0 and is
assigned S1 under the tie rule — so S3's earliest start is desk 2's
free time 4). Insist on writing both free-at values at every step; the
tie rule exists so two correct students agree.

## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect the state identified ("when
is each desk free"). Watch for: simulating in pairs without a state
variable.
Minute 1–3 — **Develop an approach.** Expect the one-desk trace
complete; a correct trace with one arithmetic slip is partial credit.
Watch for: S3 started at 2 on a free desk (there is none).
Minute 3–5 — **Compare and write.** Expect the two-desk trace underway
and the trade-off sentence drafted. If most pairs stall, run the
two-desk trace whole-class with the room calling the state.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Difficulty adaptation

- **Simplify.** Four students instead of eight; one desk only; ask for
  waits and makespan.
- **Extend.** Add a third desk and ask whether the marginal gain (wait
  and makespan) is shrinking — the start of a capacity-curve argument.
- **Hints (progressive).**
  1. *Re-orient:* "What is the smallest state that predicts the
     future? (When does each desk free?)"
  2. *Structure:* "One pass in arrival order; update one free-at value
     per student."
  3. *Near-answer:* the common wrong turn is starting a student before
     both `arrival` and `free_at` are compared — undo that choice and
     re-derive the step it breaks.

## Reference solution (pseudocode)

```
// one desk
free <- 0; total_wait <- 0
FOR EACH s IN students (by arrival):
    start <- max(s.arrival, free)
    total_wait <- total_wait + (start - s.arrival)
    free <- start + s.service
OUTPUT total_wait, free
// two desks: same loop, free becomes the pair (free1, free2),
// start <- max(arrival, min(free1, free2)), update the chosen desk.
```

## Reference solution (Python)

```python
STUDENTS = [(0, 4), (1, 3), (2, 5), (6, 2),
            (7, 4), (10, 3), (12, 2), (13, 5)]

def one_desk(students):
    free = 0
    waits = []
    for arr, svc in students:
        start = max(arr, free)
        waits.append(start - arr)
        free = start + svc
    return waits, free

def two_desks(students):
    free = [0, 0]
    waits = []
    for arr, svc in students:
        i = 0 if free[0] <= free[1] else 1   # tie -> desk 1
        start = max(arr, free[i])
        waits.append(start - arr)
        free[i] = start + svc
    return waits, max(free)

if __name__ == "__main__":
    w1, f1 = one_desk(STUDENTS)
    w2, f2 = two_desks(STUDENTS)
    print("one desk: waits", w1, f"total {sum(w1)} finish {f1}")
    print("two desks: waits", w2, f"total {sum(w2)} finish {f2}")
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.

## Edge cases

- A student arriving exactly when a desk frees — `max` resolves it; no
  wait, no idle gap.
- Two students arriving in the same minute — arrival order must be
  defined (list order here).
- A service time of zero — legal but degenerate; the trace still holds.

## Alternative approaches

- Time-stepped simulation (tick every minute) — conceptually simpler,
  far more work to trace by hand; event-driven beats it here.
- Queueing formulas (M/M/1) — wrong tool: arrivals are deterministic,
  not random; naming the mismatch is itself instructive.
- Sorting by service time (shortest-job-first) — a *different design*,
  not a comparison of the stated one; worth one sentence as fairness
  trade-off.
- **Cost.** Linear in students per design; the interesting cost is
  human trace length, which the state-size framing minimises.

## Common pitfalls

- Losing FCFS order when the second desk frees early.
- Adding service time to arrival instead of start.
- Reporting only the makespan (or only waits) and calling it "better".
- Letting desk 2 serve S3 at minute 2 — no desk is free then.

## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: "What is the smallest state that predicts everything?"
3. Walk the one-desk trace on the board, the room calling each
   `start` and `free_at`.
4. Surface the wrong turn directly: the phantom free desk at minute 2 —
   ask what the state variable says.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "event-driven trace with explicit
   state" — and hand over the discussion prompt about doubled arrivals.

## Assessment use

- **Formative use.** discussion-grade: mark state explicitness and
  rule fidelity over final numbers.
- **Mini-rubric (10 points).**
  - *Structure (2):* state variable(s) named before tracing.
  - *Method (3):* update rule applied in arrival order; tie rule used.
  - *Result (3):* one-desk 48/28 and two-desk 3/18 with per-student
    waits consistent.
  - *Communication (2):* both metrics reported; trade-off names a
    condition.
- **Follow-up check.** S3's service doubles to 10: which design's
  makespan moves more, and why?
