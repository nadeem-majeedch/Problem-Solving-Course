## Reasoning walkthrough

**Worked instance.** The app claims "0 attended" for a session that had
people in the room; the session lead wants to email the "absent" list
tonight. The only data is the export schema:
`badge_id, in_time, out_time, session, device`.

**Expected result.** demo prints the three canonical interpretations
with their required columns and one cheapest-discriminating check —
`(attendance-inferred: badge rows for session | device-health: device
heartbeat/rows | app-definition: session row semantics)` and `ask first:
did the device record anything for that session?` — plus an email
opening line that survives every interpretation because it asks rather
than accuses.

**Method — requirements, stakeholders, communication.** Walk the class
through these moves:

1. Separate the *claim* ("nobody attended") from the *data* (rows the
   app chose to write). A pipeline that records nothing is
   indistinguishable, in the export, from an empty room — that is the
   whole case.
2. Enumerate interpretations as rules with columns: (a) attended =
   has a badge row (needs badge_id + session); (b) attended = device
   was online (needs device + session — checks health, not people);
   (c) attended = app counted them (needs the app's definition — the
   session table's semantics).
3. Rank the clarifying questions by decision impact: "did the device
   record *anything* for that session?" distinguishes broken-pipeline
   from empty-room in one query — everything else follows.
4. Draft the email line that is true under all interpretations: it
   states what the system shows and asks for a reply — it does not
   assert absence.

**Where this class gets stuck.** Students want to fix the data ("just
join the door log") before agreeing on the question — the case is
deliberately schema-only to force requirements-first thinking. Expect
emails that accuse ("you missed the session") — test each draft against
the broken-pipeline world: it must stay honest there.

## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect at least two meanings of
"attended". Watch for: jumping to door-log solutions.
Minute 1–3 — **Develop an approach.** Expect three interpretations with
columns; two is partial credit if the device-health one is present.
Watch for: interpretations that need no columns (unfalsifiable rules).
Minute 3–5 — **Compare and write.** Expect the question ranked and the
email line drafted; pairs test drafts against both worlds.
Reveal and discuss — keep the reveal inside 12 minutes; this case runs
longer because the deliverable is prose, not arithmetic.

## Difficulty adaptation

- **Simplify.** Give two interpretations and ask only for the ranking
  of questions.
- **Extend.** Add a fourth column (`sync_time`) and ask which
  interpretation it enables (device offline *at sync* vs *at session*).
- **Hints (progressive).**
  1. *Re-orient:* "What is the cheapest observation that separates
     'empty room' from 'broken pipeline'?"
  2. *Structure:* "Each interpretation is a rule; every rule names the
     columns it needs."
  3. *Near-answer:* the common wrong turn is treating the export as
     ground truth — undo that choice and re-derive the step it breaks.

## Reference solution (pseudocode)

```
// The deliverable is analysis, not code; pseudocode states the rules.
attended_v1(s) <- EXISTS badge_row WHERE session = s
attended_v2(s) <- device_online(s)            // device heartbeat exists
attended_v3(s) <- app_count(s) > 0            // app's own definition
ask_first      <- "did the device record anything for that session?"
```

## Reference solution (Python)

```python
SCHEMA = ["badge_id", "in_time", "out_time", "session", "device"]

def interpretations():
    return {
        "attendance-inferred": ["badge_id", "session"],
        "device-health": ["device", "session"],
        "app-definition": ["session"],
    }

if __name__ == "__main__":
    print(" | ".join(f"{k}:{'+'.join(v)}" for k, v in interpretations().items()))
    print("ask first: did the device record anything for that session?")
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.

## Edge cases

- A badge row with `out_time` missing — attended under v1 either way.
- The device that was offline is also the one the door log needs —
  independence of evidence is not free.
- The session lead's request deadline (tonight) — requirements work
  under time pressure still beats a wrong blast email.

## Alternative approaches

- Answer nothing and query the door log directly — fastest, but the
  door log lives in another team's system; the case restricts access
  to make the asking behaviour visible.
- Send the email with a caveat paragraph — halfway honesty; discuss
  why caveats do not undo an accusation.
- Redefine the report as "badges seen" instead of "attended" — the
  strongest long-term fix: change the claim to match the data.
- **Cost.** No computational cost exists; the scarce resource is one
  clarifying question sent before the deadline.

## Common pitfalls

- Treating the export as ground truth about the room.
- Writing emails that are false in the broken-pipeline world.
- Interpretations that name no columns (unfalsifiable).
- Ranking questions by ease instead of decision impact.

## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: "What is the cheapest observation that separates 'empty
   room' from 'broken pipeline'?"
3. Build the three interpretations as a table on the board: rule,
   columns, what world it assumes.
4. Surface the wrong turn directly: export-as-ground-truth — ask what
   the export would look like if the device was offline.
5. Show the reference summary, then workshop two student email drafts
   against the broken-pipeline world.
6. Close by naming the technique — "requirements before repair" — and
   hand over the discussion prompt about the door-log answer.

## Assessment use

- **Formative use.** discussion-grade: mark interpretation quality and
  the honesty of the email draft under both worlds.
- **Mini-rubric (10 points).**
  - *Structure (2):* interpretations stated as rules with columns.
  - *Method (3):* question ranked by decision impact; email drafted.
  - *Result (3):* three valid interpretations, one dominant question,
    an email line honest in both worlds.
  - *Communication (2):* no accusatory language; assumptions named.
- **Follow-up check.** The app team answers "the device was offline."
  Which interpretation dies, which survives, and what does the session
  lead owe the students?
