## Reasoning walkthrough

**Worked instance.** Eight logged incidents across three systems, with
one genuine overlap (W1's Monday pair, 09:10–09:40 and 09:30–10:00).

**Expected result.** demo prints `merged minutes: {'DB': 55, 'W1': 80,
'W2': 80}`, the six-entry cause table, and `flag: W1 ( 3 incidents )`
— W1's raw 90 minutes shrink to 80 once the Monday overlap is merged;
DB totals 55 from two disjoint software incidents; the coded flag rule
"most incidents, first system on ties" selects W1 — and W2 ties it on
count, which is itself a discussion point.

**Method — reliability, aggregation, data.** Walk the class through
these moves:

1. Decide the aggregation rule before totalling: for "how reliable was
   each system?", two simultaneous network incidents are one outage —
   merge overlapping intervals per system, then sum. State the choice
   in the answer; the raw number goes alongside it.
2. Merge per system: sort intervals, fold any interval starting
   before the current end into it. W1 Monday: 09:10–10:00 = 50, not
   60; plus Wednesday 30 → 80.
3. Cause table: a dictionary keyed by (system, cause) turns eight
   lines into six counts — network: W1×2, W2×1; power: W1×1, W2×2;
   software: DB×2.
4. Flag with a rule, not a vibe: the coded rule (most incidents,
   first system on ties) picks W1 — but W2 ties it at three
   incidents and spreads them over two causes, so the *discussion*
   can reasonably argue W2 is the sharper target. The lesson: when a
   tie is possible, the tie-break is part of the answer.

**Where this class gets stuck.** Students sum durations first and ask
questions later — force the merge-or-double-count sentence before any
arithmetic. Second stall: treating W1's overlap as "two incidents, 60
minutes" — draw the timeline; the overlap is visible, not computed.

## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect the overlap spotted (or its
absence queried). Watch for: summing immediately.
Minute 1–3 — **Develop an approach.** Expect per-system totals with
the merge decision stated; correct minutes with an unstated rule is
partial credit. Watch for: merging W1's Wednesday into Monday
(non-overlapping).
Minute 3–5 — **Compare and write.** Expect the cause table and the
flagged system justified; pairs compare flag rules.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Difficulty adaptation

- **Simplify.** One system (W1) only — ask for raw vs merged minutes.
- **Extend.** Add an incident spanning two systems (a shared switch);
  ask where its minutes belong and what the merge rule does with it.
- **Hints (progressive).**
  1. *Re-orient:* "List W1's Monday incidents on a timeline before
     computing anything."
  2. *Structure:* "Sort intervals, fold overlaps, then sum; causes go
     in a (system, cause) dictionary."
  3. *Near-answer:* the common wrong turn is double-counted overlap —
     undo that choice and re-derive the step it breaks.

## Reference solution (pseudocode)

```
FOR EACH system:
    intervals <- sort incidents of system by start
    total <- fold intervals, merging overlaps
OUTPUT merged minutes per system
causes <- dictionary {(system, cause): count}
flag <- system with most incidents (tie-break: more causes)
```

## Reference solution (Python)

```python
LOG = [
    ("W1", 9 * 60 + 10, 9 * 60 + 40, "network"),
    ("W1", 9 * 60 + 30, 10 * 60, "network"),
    ("W2", 9 * 60 + 20, 9 * 60 + 50, "power"),
    ("DB", 14 * 60, 14 * 60 + 25, "software"),
    ("W1", 8 * 60, 8 * 60 + 30, "power"),
    ("W2", 8 * 60 + 10, 8 * 60 + 40, "power"),
    ("DB", 16 * 60 + 45, 17 * 60 + 15, "software"),
    ("W2", 10 * 60, 10 * 60 + 20, "network"),
]

def merged_minutes(sysname):
    iv = sorted((s, e) for sy, s, e, _ in LOG if sy == sysname)
    total, cs, ce = 0, iv[0][0], iv[0][1]
    for s, e in iv[1:]:
        if s > ce:
            total += ce - cs
            cs, ce = s, e
        else:
            ce = max(ce, e)
    return total + (ce - cs)

if __name__ == "__main__":
    systems = sorted({sy for sy, *_ in LOG})
    print("merged minutes:", {sy: merged_minutes(sy) for sy in systems})
    causes = {}
    for sy, _, _, c in LOG:
        causes[(sy, c)] = causes.get((sy, c), 0) + 1
    print("cause table:", dict(sorted(causes.items())))
    counts = {}
    for sy, *_ in LOG:
        counts[sy] = counts.get(sy, 0) + 1
    flag = max(counts, key=counts.get)
    print("flag:", flag, "(", counts[flag], "incidents )")
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.

## Edge cases

- An incident entirely inside another — the fold must not double-count
  the inner interval's tail.
- Two systems sharing one root cause (network switch) — per-system
  minutes still correct; the *cause* pattern is where it shows.
- Zero-duration incidents (logged, instantly fixed) — count them in
  the cause table; they contribute no minutes.

## Alternative approaches

- Report raw sums only — simpler and wrong for W1's question; keep it
  as the contrast column, not the answer.
- Union-of-intervals via a boolean timeline per minute — concrete and
  visual; at this scale either works, the fold scales better.
- Pivot table by (system, cause) — the spreadsheet version of the
  dictionary; naming both shows the same computation in two coats.
- **Cost.** Sorting per system dominates: O(k log k) per system,
  linear in incidents overall — trivial here, and the pattern to
  reuse at log scale.

## Common pitfalls

- Summing before deciding the merge rule.
- Merging intervals that merely share an endpoint with an overlap.
- Reading the cause table as downtime (counts ≠ minutes).
- Flagging by minutes alone when incidents tell the sharper story.

## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: "Where does W1's Monday overlap show in your total?"
3. Draw the three timelines on the board; fold each aloud.
4. Surface the wrong turn directly: the 90 vs 80 gap — ask what the
   extra 10 minutes claims happened.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "merge-then-aggregate with stated
   rules" — and hand over the discussion prompt about uptime.
