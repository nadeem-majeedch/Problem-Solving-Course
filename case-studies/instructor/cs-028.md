## Reasoning walkthrough

**Worked instance.** defect vanishes when print(i) is added to the loop

**Expected result.** candidates: loop mutates the list it iterates; set iteration order; time-dependent state

**Method — systematic debugging.** Walk the class through these moves:

1. Reproduce the defect with the smallest input that shows it.
2. State hypotheses: what could make the output wrong?
3. Test one hypothesis at a time with prints or asserts at the boundary.
4. Localise the fault to a line, explain the mechanism, fix minimally.
5. Add the regression test that would have caught it.

**Where this class gets stuck.** Print changes timing, not logic - unless the loop iterates something the print rebuilds; enumerate while mutating is the classic. Expect the first
five minutes to produce changing two things at once destroys the evidence as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step
computation on the instance; a correct rule with an arithmetic slip is
partial credit. Watch for: mutating the input collection the caller still holds while scanning it.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder
(below) whole-class rather than pair by pair.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (pseudocode)

FUNCTION buggy_remove(items, target)
    FOR EACH x IN items DO
        IF x = target THEN
            items.remove(x)
    RETURN items
FUNCTION fixed_remove(items, target)
    RETURN {x for each x in items AND x != target}
// demo run: OUTPUT buggy_remove([1, 2, 2, 3], 2)
// demo run: OUTPUT fixed_remove([1, 2, 2, 3], 2)


## Reference solution (Python)

```python
def buggy_remove(items, target):
    for x in items:            # BUG: mutating while iterating
        if x == target:
            items.remove(x)
    return items

def fixed_remove(items, target):
    return [x for x in items if x != target]

if __name__ == "__main__":
    print(buggy_remove([1, 2, 2, 3], 2))   # [1, 2, 3] - one survives
    print(fixed_remove([1, 2, 2, 3], 2))   # [1, 3]
```

The code is runnable as-is; executing the file prints the worked instance
so you can demo it live on the projector.


## Edge cases

- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.


## Alternative approaches

- Print changes timing, not logic - unless the loop iterates something the print rebuilds; enumerate while mutating is the classic.
- Loop-first formulation versus a comprehension/direct-expression formulation — same result, different emphasis on state versus intent.
- A table filled by hand before any code: for the size of instance here it is both a solution and the test oracle.
- **Cost.** Linear: one visit per item, a constant amount of work per visit; the alternatives shift exactly this cost.


## Common pitfalls

- Changing two things at once destroys the evidence.
- Mutating the caller's list when the result was meant to be a fresh one — the demo where the input 'changes by itself'.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'What does the wrong output tell you about where the program's state first leaves the intended path?'
3. Walk the worked instance (defect vanishes when print(i) is added to the loop) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'changing two things at once destroys the evidence' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "systematic debugging" — and hand over the
   discussion prompt: **"Which hypothesis did you rank first, and what evidence moved it down the list?"**


## Assessment use

- **Formative use.** discussion-grade: mark assumption quality and rule precision rather than the final number, and expect the full cycle to run long.
- **Mini-rubric (10 points).**
  - *Structure (2):* inputs, outputs, and the binding constraint named before any computation.
  - *Method (3):* the stated moves executed — especially "State hypotheses: what could make the output wrong?"
    and "Test one hypothesis at a time with prints or asserts at the boundary".
  - *Result (3):* the worked instance computed correctly (candidates: loop mutates the list it iterates; set iteration…),
    and the answer survives the smallest and the boundary input.
  - *Communication (2):* assumptions stated; the answer reports which rule produced it.
- **Follow-up check.** State the deciding rule in one sentence and apply it to a half-size version of the worked instance.
