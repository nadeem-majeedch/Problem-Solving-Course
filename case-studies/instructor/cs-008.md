## Reasoning walkthrough

**Worked instance.** playlist A(pop), B(pop), C(jazz), D(pop), E(jazz)

**Expected result.** e.g. A, C, B, E, D - all songs once, no two same-artist adjacent; same-artist-majority needs a repair rule

**Method — modelling, rules, and decisions.** Walk the class through these moves:

1. Extract the entities, quantities, and rules from the story.
2. State assumptions explicitly (what is fixed, what varies).
3. Write the decision procedure as precise rules.
4. Run the rules on the worked instance; sanity-check the output.

**Where this class gets stuck.** Greedy: place songs round-robin by artist, then fix remaining pairs by reinsertion. Expect the first
five minutes to produce hiding a value judgement inside 'obvious' arithmetic as the
most common wrong turn; plan the reveal around it.

## Reference solution (pseudocode)

FUNCTION shuffle_playlist(songs)
    by_artist <- map{}
    FOR EACH s IN songs DO
        append s to by_artist.setdefault(s[1], [])
    queues <- {by_artist[a] for each a in by_artist}
    queues.sort()
    result <- []
    WHILE queues DO
        queues.sort()
        nxt <- queues[0]
        IF (result) AND (nxt[0][1] = result[-1][1]) AND (LENGTH(queues) > 1) THEN
            nxt <- queues[1]
        append nxt.pop(0) to result
        IF NOT nxt THEN
            queues.remove(nxt)
    RETURN result
// demo run: OUTPUT {t for each (t, _) in shuffle_playlist(songs)}


## Reference solution (Python)

```python
def shuffle_playlist(songs):
    """songs: list of (title, artist). Returns a shuffle with no two
    same-artist neighbours when possible; appends leftovers otherwise."""
    by_artist = {}
    for s in songs:
        by_artist.setdefault(s[1], []).append(s)
    queues = [by_artist[a] for a in by_artist]
    queues.sort(key=len, reverse=True)
    result = []
    while queues:
        queues.sort(key=len, reverse=True)
        nxt = queues[0]
        if result and nxt[0][1] == result[-1][1] and len(queues) > 1:
            nxt = queues[1]
        result.append(nxt.pop(0))
        if not nxt:
            queues.remove(nxt)
    return result

if __name__ == "__main__":
    songs = [("A", "pop"), ("B", "pop"), ("C", "jazz"), ("D", "pop"), ("E", "jazz")]
    print([t for t, _ in shuffle_playlist(songs)])
```

## Edge cases

- Termination: name the update that guarantees the loop ends, and check it on the smallest input.
- First occurrence of a key not yet in the map — the default path must produce a defined answer.
- Ties: two equal values may swap order in the input; the stated rule must pin the output.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.


## Alternative approaches

- Greedy: place songs round-robin by artist, then fix remaining pairs by reinsertion.
- Rewrite the while-loop as a bounded for-loop over the data (or vice versa) and compare which version makes termination obvious.
- Sort first, then scan once, versus scanning with extra bookkeeping and no sort: the sort pays for itself only when later steps reuse the order.
- **Cost.** The sort dominates the cost: n log n in the input size, everything after it is one cheap pass; the alternatives shift exactly this cost.


## Common pitfalls

- Hiding a value judgement inside 'obvious' arithmetic.
- An update path that never moves the state — the loop that never ends; test on an interval of size two.
- Reading a key before it exists (the first occurrence) instead of using the default path.
- Mutating the caller's list when the result was meant to be a fresh one — the demo where the input 'changes by itself'.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.

1. Display the case and start the timer (5 minutes). While students work,

2. Ask first: 'Which quantity does the rule attach to, and what exactly does one application of the rule change?'
3. Walk the worked instance (playlist A(pop), B(pop), C(jazz), D(pop), E(jazz)) on the board

4. Surface the wrong turn directly: 'hiding a value judgement inside 'obvious' arithmetic' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "modelling, rules, and decisions" — and hand over the
