## Reasoning walkthrough

**Worked instance.** 100 lockers, 100 students; student i toggles lockers divisible by i

**Expected result.** open lockers are perfect squares: 1, 4, 9, 16, 25, 36, 49, 64, 81, 100

**Method — counting and probability.** Walk the class through these moves:

1. Frame the question: how many outcomes, and how many favourable?
2. Decide ordered vs unordered, with vs without replacement — in words first.
3. Compute with the multiplication/addition principles (or complements).
4. Check the count by brute-force enumeration when small.

**Where this class gets stuck.** Locker n is toggled once per divisor of n; divisors pair up (d, n/d) - except squares, where d = n/d. Expect the first
five minutes to produce adding situations that multiply (wearing a shirt and trousers) as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step

partial credit. Watch for: rounding mid-computation on the input values instead of once at the end.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder

Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (pseudocode)

FUNCTION open_lockers(n)
    RETURN {k for each k in range 1..n + 1 AND INTEGER(k ^ 0.5) ^ 2 = k}
FUNCTION open_lockers_sim(n)
    lockers <- [false] * (n + 1)
    FOR EACH student IN range 1..n + 1 DO
        FOR EACH locker IN range student, n + 1, student DO
            lockers[locker] <- NOT lockers[locker]
    RETURN {i for each i in range 1..n + 1 AND lockers[i]}
// demo run: OUTPUT open_lockers()


## Reference solution (Python)

```python
def open_lockers(n=100):
    return [k for k in range(1, n + 1) if int(k ** 0.5) ** 2 == k]

def open_lockers_sim(n=100):
    lockers = [False] * (n + 1)
    for student in range(1, n + 1):
        for locker in range(student, n + 1, student):
            lockers[locker] = not lockers[locker]
    return [i for i in range(1, n + 1) if lockers[i]]

if __name__ == "__main__":
    assert open_lockers() == open_lockers_sim()
    print(open_lockers())
```

## Edge cases

- Empty or single-item input: decide what is returned and what must NOT be printed.
- Boundary positions: the first item, the last item, and the position one past each end (the i-1 / i+1 arithmetic).
- Rounding: say where values are rounded and why a last digit may differ between two correct attempts.


## Alternative approaches

- Locker n is toggled once per divisor of n; divisors pair up (d, n/d) - except squares, where d = n/d.
- Loop-first formulation versus a comprehension/direct-expression formulation — same result, different emphasis on state versus intent.
- A table filled by hand before any code: for the size of instance here it is both a solution and the test oracle.
- **Cost.** Logarithmic: the interval (or exponent) halves every step, so doubling the input adds one step; the alternatives shift exactly this cost.


## Common pitfalls

- Adding situations that multiply (wearing a shirt and trousers).
- Comparing floating-point values for exact equality instead of a tolerance (or rounding at the very end, not mid-computation).
- Off-by-one at the boundary: the update that is correct for the middle of the data and wrong at the two ends.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,

2. Ask first: 'Are you counting arrangements, selections, or successes — and does order matter here?'
3. Walk the worked instance (100 lockers, 100 students; student i toggles lockers divisible by i) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'adding situations that multiply (wearing a shirt and trousers)' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "counting and probability" — and hand over the
   discussion prompt: **"When is enumeration a legitimate answer rather than a crutch?"**
