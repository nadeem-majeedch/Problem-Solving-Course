## Reasoning walkthrough

**Worked instance.** grid = [[0]*3]*2; grid[0][0] = 9

**Expected result.** both rows become [9, 0, 0] - the two rows are one object; fix: [[0]*3 for _ in range(2)]

**Method — list surgery and slicing.** Walk the class through these moves:

1. Decide whether to mutate in place or build a new list.
2. Express the rearrangement with slices before writing loops.
3. Handle the wrap-around / size cases explicitly.
4. Check aliasing: who else can see this list object?

**Where this class gets stuck.** Print id(grid[0]) and id(grid[1]) - identical ids convict the alias immediately. Expect the first
five minutes to produce assigning a list to another name copies the reference, not the contents as the
most common wrong turn; plan the reveal around it.


## Five-minute teaching sequence

Minute 0–1 — **Read and analyse.** Expect inputs, outputs, and at least
one stated assumption named; the deciding quantity here is the input
rule. Watch for: retelling the story without extracting the decision.
Minute 1–3 — **Develop an approach.** Expect a rule or a first-step
computation on the instance; a correct rule with an arithmetic slip is
partial credit. Watch for: a rule that reads correctly but computes on the wrong quantity in the input data.
Minute 3–5 — **Compare and write.** Expect the update rule or loop
skeleton written down, pairs comparing orders of operations. If most
pairs stall, give the structure hint from the difficulty ladder
(below) whole-class rather than pair by pair.
Reveal and discuss — keep the reveal inside 10 minutes so the exit question still fits.

## Reference solution (Python)

```python
def make_grid_buggy(rows, cols):
    return [[0] * cols] * rows

def make_grid_fixed(rows, cols):
    return [[0] * cols for _ in range(rows)]

if __name__ == "__main__":
    g = make_grid_buggy(2, 3)
    g[0][0] = 9
    print(g)                    # [[9,0,0],[9,0,0]]
    f = make_grid_fixed(2, 3)
    f[0][0] = 9
    print(f)                    # [[9,0,0],[0,0,0]]
```

so you can demo it live on the projector.

## Common pitfalls

- Assigning a list to another name copies the reference, not the contents.
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.


## Reveal script

1. Display the case and start the timer (5 minutes). While students work,
   circulate and read shoulders; pick one conventional attempt and one
   surprising one for the board.
2. Ask first: 'Does this operation need a copy, a view, or in-place surgery — and who else can still see the list?'
3. Walk the worked instance (grid = [[0]*3]*2; grid[0][0] = 9) on the board
   under the stated rule before any code appears; the class calls the
   next state at each step.
4. Surface the wrong turn directly: 'assigning a list to another name copies the reference, not the contents' — ask the room
   which quiet assumption it makes.
5. Show the reference Python, run it on the worked instance, and let the
   class compare with their own answers.
6. Close by naming the technique — "list surgery and slicing" — and hand over the
   discussion prompt: **"When is the extra memory of slicing worth it, and when would you insist on in-place?"**

- **Follow-up check.** State the deciding rule in one sentence and apply it to a half-size version of the worked instance.
