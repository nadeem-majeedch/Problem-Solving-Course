## Reference solution (pseudocode)

FUNCTION free_starts(busy, day_lo, day_hi, meeting)
    starts <- []
    cursor <- day_lo
    FOR EACH (b_start, b_end) IN SORTED(busy) DO
        IF b_start - cursor >= meeting THEN
            t <- cursor
            WHILE t + meeting <= b_start DO
                append t to starts
                t <- t + 0.5
        cursor <- MAX(cursor, b_end)
    WHILE cursor + meeting <= day_hi DO
        append cursor to starts
        cursor <- cursor + 0.5
    RETURN starts
// demo run: OUTPUT free_starts([(9, 10), (11, 12.5)])


## Reference solution (Python)

```python
def free_starts(busy, day_lo=8, day_hi=18, meeting=1.5):
    """Return all meeting start times fitting around sorted busy intervals."""
    starts = []
    cursor = day_lo
    for b_start, b_end in sorted(busy):
        if b_start - cursor >= meeting:
            t = cursor
            while t + meeting <= b_start:
                starts.append(t)
                t += 0.5
        cursor = max(cursor, b_end)
    while cursor + meeting <= day_hi:
        starts.append(cursor)
        cursor += 0.5
    return starts

if __name__ == "__main__":
    print(free_starts([(9, 10), (11, 12.5)]))
```

## Edge cases

- Termination: name the update that guarantees the loop ends, and check it on the smallest input.
- Ties: two equal values may swap order in the input; the stated rule must pin the output.
- Empty or single-item input: decide what is returned and what must NOT be printed.
- Degenerate values: zero, negatives, and duplicates among the instance's data.
- Rounding: say where values are rounded and why a last digit may differ between two correct attempts.


## Alternative approaches

- Walk the sorted busy list keeping 'free from' marker; a start works if the whole meeting fits before the next busy block.
- Several passes with built-in helpers (a sum here, a max there) instead of one pass with several accumulators — clearer to read, more visits over the data.
- Sort first, then scan once, versus scanning with extra bookkeeping and no sort: the sort pays for itself only when later steps reuse the order.
- **Cost.** The sort dominates the cost: n log n in the input size, everything after it is one cheap pass; the alternatives shift exactly this cost.


## Common pitfalls

- Initialising best to 0 breaks when all values are negative or below target.
- An update path that never moves the state — the loop that never ends; test on an interval of size two.
- Mutating the caller's list when the result was meant to be a fresh one — the demo where the input 'changes by itself'.
- Comparing floating-point values for exact equality instead of a tolerance (or rounding at the very end, not mid-computation).
- Reporting the answer without the rule that produced it — the decision becomes uncheckable.
